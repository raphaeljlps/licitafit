API CruzaEdital para embutir matching no seu produto

Para fundadores e líderes de produto de ERP, comercial/AFV e verticais de TI cujos clientes atuam em compras públicas. Vocês continuam donos da interface e do relacionamento; nós entregamos matching de catálogo a oportunidades do PNCP.

O problema do vendor de software

Clientes distribuidores de TI pedem “licitações no ERP”. Montar isso por conta própria significa ingestão contínua do PNCP, matching com o catálogo de cada cliente, alertas quando o edital muda, e UI que não confunde matching com habilitação.

  • Manter pipeline de dados públicos não é o core do ERP
  • Alerta por palavra-chave ou CNAE não prioriza com o catálogo real
  • A feature precisa de status claros (matched, conflito, unknown, needs_review)
  • Isolamento por cliente e feedback de match entram no desenho desde o início

Antes de prometer a feature, use o checklist de oportunidades no ERP.

O que a API entrega

Matching consciente de catálogo e eventos para a UI do parceiro (sem transferir a propriedade da experiência do cliente).

Ingestão e versões

Coleta registros relevantes no PNCP, guarda identificadores e versões, e revisita oportunidades monitoradas quando há alteração.

Matching catálogo ↔ item

Compara produtos do cliente com itens do edital, inspeciona documentos selecionados e devolve explicações. Requisitos ilegíveis ficam em aberto (unknown).

API de parceiro

Chaves, upload de catálogo, listagem de oportunidades, feedback de match e webhooks (sem o parceiro manter pipeline próprio de dados públicos).

Apoio à decisão comercial (não parecer jurídico nem garantia de habilitação). Detalhe em limites do matching.

Como embute no ERP / AFV

  1. Criar catálogo e enviar produtos

    POST /v1/catalogs e PUT /v1/catalogs/{id}/products com o mix do cliente (catálogo de TI em geral).

  2. Listar oportunidades na UI

    GET /v1/catalogs/{id}/opportunities alimenta a feature “oportunidades alinhadas ao catálogo” (o que mostrar na tela).

  3. Feedback e webhooks

    POST /v1/opportunities/{id}/feedback e POST /v1/webhook-endpoints para correção de matches e alertas de mudança.

Passo a passo: como embutir matching de catálogo no ERP. Visão de endpoints: integração API.

Para quem é a API

O usuário final continua sendo a equipe comercial ou de vendas ao governo do distribuidor (a feature fica embutida no software do parceiro).

ERP de distribuição / atacado

Feature “oportunidades de governo alinhadas ao catálogo” no ERP que o distribuidor já usa.

Software comercial / AFV

Triagem de oportunidades públicas ligada aos SKUs do cliente, no app de força de vendas.

Catálogo de TI

Softwares para distribuidores de hardware que vendem a governo (catálogo de TI em geral).

Compras públicas no stack

Complemento opcional de matching e alertas (sem substituir portais de disputa).

Perguntas frequentes

A API substitui a UI do meu ERP?

Não. Vocês continuam donos da interface e do relacionamento. A API entrega matching, oportunidades e eventos; a feature aparece no software do parceiro.

Quanto custa a API para parceiros?

R$ 50 por 1.000 requests, com mínimo de R$ 490/mês, e R$ 1,90 por licitação monitorada / mês.

O matching garante habilitação?

Não. O CruzaEdital é apoio à decisão comercial. Status matched, conflito, unknown e needs_review orientam revisão humana; não constituem parecer jurídico nem garantia de habilitação.

Feed do PNCP já resolve?

Ingestão bruta do PNCP não substitui matching com o catálogo do cliente. Ver feed PNCP vs matching.
