Feed bruto do PNCP vs produto de matching de catálogo

O feed ou a API de consulta do PNCP entrega dados públicos de contratações. Um produto de matching cruza esses dados com o catálogo do distribuidor, devolve status de requisitos e pede revisão humana no ERP — sem afirmar habilitação jurídica.

Quando o feed basta

Engenharia quer controle total da ingestão; o produto ainda não tem catálogo do cliente; ou o objetivo é só espelhar publicações oficiais sem priorização por SKU.

A documentação oficial do PNCP (portal e manuais de consulta) é a referência para comportamento da API pública — use sempre as fontes oficiais.

Quando o matching entra

O ERP precisa mostrar oportunidades alinhadas ao catálogo, com requisitos a conferir e alertas quando o edital muda. O parceiro evita manter sozinho o ciclo completo de parsing + cruzamento + impacto.

Ver também alerta genérico vs matching e o vocabulário de status.

Build vs buy do pipeline (visão de produto)

Construir por conta própria significa assumir ingestão contínua, tratamento de atualizações, qualidade de documentos e a lógica de matching. Comprar um produto de matching significa consumir esses resultados via API e manter a UI e o relacionamento no ERP.

Nenhum dos caminhos é “sempre certo”. O checklist de oportunidades no ERP lista o que alinhar antes de vender a feature — ingestão, catálogo, UI de revisão, webhooks, isolamento e disclaimer comercial.

Perguntas frequentes

O que é o feed ou a API de consulta do PNCP?

É a forma pública de consultar contratações publicadas no Portal Nacional de Contratações Públicas: registros, documentos e mecanismos de atualização descritos na documentação oficial. Entrega dados — não decide quais SKUs do seu catálogo merecem atenção.

Por que só o feed pode não bastar no ERP do distribuidor?

Porque a equipe comercial precisa priorizar editais com base nos produtos que já vende. Sem cruzamento com o catálogo e status de requisitos, a triagem fina continua manual.

Matching de catálogo substitui o PNCP?

Não. O matching depende de dados públicos e acrescenta cruzamento com o catálogo, status e alertas de impacto. Não substitui a fonte oficial nem constitui habilitação jurídica.

Construir o pipeline internamente é sempre pior?

Não. Faz sentido quando a engenharia quer controle total da ingestão. O ponto de decisão é o custo contínuo de manter o pipeline versus consumir uma API de parceiro e manter a UI no ERP.
